# Internationalization (i18n)

## Context

The site serves German (default) visitors and also English, French, Italian, Russian, and Dutch. Inline `{ de, en }[locale]` literals do not
scale: a third locale multiplies every call site, inflates React modules, and drowns coding-agent context. Routing, SEO (`hreflang`,
sitemap), profile language, and display formatting still need a single locale model.

Switzerland is a **region**, not a UI language. A German-speaking user in Zurich uses `de`; `Intl` may later use `de-CH` from country.

## Decision

**Optional path parameter `{-$locale}`** (TanStack Router) for locale routing, plus **JSON message catalogs** with type-safe key access via
i18next. The library is messages only. It does not own URLs, cookies, or `Users.locale`.

- Default locale is `de` (unprefixed URLs: `/`, `/about`). Other locales are prefixed: `/en`, `/fr`, `/it`, `/ru`, `/nl`, `/en/about`.
- Public locales (`Locale` / `CatalogLocale`: `'de' | 'en' | 'fr' | 'it' | 'ru' | 'nl'`) live in `src/shared/locale.ts` as
  `CATALOG_LOCALES`. That same set is used on URLs, `Users.locale`, GraphQL `enum Locale`, the language switcher, Accept-Language redirect,
  sitemap, and `hreflang`. Web-only helpers (`localeFromAcceptLanguage`, `localeFromParam`) re-export those types from
  `src/web/utils/locale.ts`.
- `languageTagFromLocale(locale)` maps to BCP-47 tags used by `Intl`: `de` → `de-DE`, `en` → `en-US`, `fr` → `fr-FR`, `it` → `it-IT`, `ru` →
  `ru-RU`, `nl` → `nl-NL`. Region overlays (`de-CH` / `fr-CH` / `it-CH` from country) are a follow-on; do not add a UI locale for Swiss
  German.
- `src/routes/{-$locale}.tsx` `beforeLoad` 404s unknown locale prefixes, and auto-redirects first-time visitors from `Accept-Language` /
  `locale` cookie when the preferred locale is not the default. Redirects and language switches go through `buildLocaleHref` /
  `buildLocalePath` / `pathWithoutLocale`, which strip every leading non-default locale segment from the path before re-prefixing so a stale
  match or mismatched claimed locale cannot produce `/en/en/…`, and keep the current `searchStr` / `hash` so deep links like `?tab=`
  survive. Isomorphic path helpers `localePath` / `pathWithoutLocale` live in `src/shared/locale.ts` (re-exported from
  `src/web/utils/locale.ts`) so server-built email and WhatsApp links prefix every non-default locale the same way as the router.
- Components read locale via `useLocale()` (`src/web/hooks/useLocale.ts`). UI copy uses `useT(namespace)` / isomorphic `t(locale, ns, key)`.
  `I18nProvider` wraps RootDocument chrome with `common` so SessionStartupGates (locale mismatch, legal, cookie) can call `useT` outside the
  locale layout; the locale layout nested provider then adds page namespaces. The language switcher (`LanguageSwitcher`) sets the cookie and
  navigates; on public pages with a `Footer` (landing, sign-in) it lives in the footer bottom bar as quiet native-language text links styled
  like the adjacent legal links, not ISO codes or filled pills.
- **Signed-in profile language** — `Users.locale` is mandatory (`NOT NULL`, DB default `de`). Self-registration stamps the current UI locale
  via `UserCreate.locale`; admin create defaults to `de`. Transactional lifecycle/job emails resolve locale from each recipient’s
  `Users.locale` (OTP and gift-card purchase still use request-time / snapshot locale for guests). When a signed-in user’s route locale
  differs from `Users.locale`, `LocaleMismatchGate` (first in the root startup pipeline) shows a non-dismissible dialog: confirm updates the
  profile (+ cookie) via a locale-only `userUpdate` that is allowed while legal acceptance is still pending; decline redirects to the
  profile-locale href (+ cookie), preserving query and hash. Admin Sign in as skips this gate so the operator does not rewrite
  `Users.locale`. No `Sessions.locale`. Pipeline order: [session-startup-gates.md](../features/session-startup-gates.md).
- **Signed-in profile time zone** — `Users.timeZone` is mandatory (`NOT NULL`, DB default `Europe/Berlin`, IANA id). Self-registration
  stamps the browser zone via `UserCreate.timeZone`; admin create defaults to `Europe/Berlin` when omitted. Users edit it on Account; admins
  on the user general form. GraphQL validates with `graphql-scalars` `TimeZone`. `SessionStartupGates` loads `user.timeZone` into
  `TimeZoneProvider`; UI calls `useTimeZone()` and passes `{ locale, timeZone }` into shared date/time formatters. Anonymous visitors fall
  back to the browser zone (SSR: `DEFAULT_TIME_ZONE`). User-facing emails that format absolute times use the **recipient** `Users.timeZone`.
  Cook call wall-clock derivation uses the **cook’s** `Users.timeZone`. Slack ops and Berlin-fixed jobs stay on their own constants.
  **Offer-connected clock times** use `formatBookingWhen*` in `src/shared/formatBookingWhen.ts`. Mismatch is a UTC-offset difference at that
  instant, not an IANA-id compare (`Europe/Berlin` vs `Europe/Zurich` stays unlabeled). Dinner / in-person event times are **venue-primary**
  (IANA from `exactEventAddress.country`; DACH → Berlin family). When the viewer’s offset differs, the primary line adds the city
  (`in München`) and a muted secondary line is `13:00 in deiner Zeitzone` / `1:00 PM in your time zone`. Discovery calls are
  **viewer-primary**; on offset mismatch a second line names the peer (`12:00–12:15 Uhr für Anna (New York)`). Slot pickers stay single-time
  with one caption (`Zeiten in deiner Zeitzone. Anna ist in New York (6 Stunden hinter dir).`). Zone labels are city-style, never raw IANA
  except admin secondary ops lines. Date-only cards format the calendar day in the venue zone. ICS `DTSTART` stays UTC; the description uses
  venue time plus city. Emails and WhatsApp reuse the same helpers (recipient still gets their secondary line). Peer zones for cook and
  customer offer surfaces are on offer-scoped GraphQL (`cookTimeZone` / `customerTimeZone`), not `PublicUser`. Admin reads nested
  `AdminUser.timeZone` (`cook.user.timeZone` / `bookingRequest.customer.timeZone`).
- **Display formatting** (dates, times, date ranges, month/year, participants, currency, file sizes, durations) uses isomorphic helpers in
  `src/shared` — `formatDate`, `formatTime`, `formatDateTime`, `formatDateRange`, `formatMonthYear`, `formatParticipants`, `formatCurrency`,
  `formatBytes`, `formatDuration`, `formatHms`, plus storage helper `formatIsoDate` and form helpers `centsToEuros` / `eurosToCents`.
  Locale-aware display helpers take a required `{ locale }` options object and derive the language tag internally via
  `languageTagFromLocale`. **Do not format dates or money inside i18n messages**; interpolate already-formatted strings. `formatCurrency`
  defaults to **2 fraction digits** for cook, customer, and offer-price surfaces; amounts under 1 € fall back to localized cents via
  `common.currency.cents`. Only admin overview summaries may pass `maximumFractionDigits: 0`. Date/time helpers accept an optional
  `timeZone` (viewer via `useTimeZone()`, recipient in emails, cook zone for call-slot derivation; Slack stays on its ops constant). Prefer
  these over local `Intl` / `date-fns` formatters in routes, emails, and Slack. Import from `src/shared` (barrel).
- **Server-built UI copy on GraphQL** (e.g. offer `costBreakdown` line titles from `bookingRequestOfferCostBreakdownBuild`) must use the
  **viewer** `Users.locale` threaded through the role hydrate (`userBookingRequestHydrate` / `cookBookingRequestOfferHydrate` /
  `adminBookingRequestHydrate` / `adminBookingRequestOfferHydrate`). Load missing parents via `userLocaleRequire` — do not hardcode `de` or
  fall back to `DEFAULT_LOCALE` for those strings. Prefer `t(locale, …)` from `src/i18n` over inline maps.
- Calendar widgets and relative time (`formatDistanceToNow*`) still use `DATE_FNS_LOCALE` from `src/web/utils/dateFnsLocale.ts` — `date-fns`
  needs its own locale objects and is not inferred from the route. The shared `Calendar` month-dropdown formatter uses that locale's `code`
  (not the browser default) so `/en/...` visitors see English month names even when the OS is German.

### Message catalogs

JSON is the product. i18next is the current adapter (web + Node). A future mobile app in this repo reads the same files.

```text
src/i18n/
  locales/{de,en,fr,it,ru,nl}/{namespace}.json
  catalogLoaders.ts      # explicit dynamic import map (Vite-analyzable); no email
  emailCatalogLoaders.ts # server-only
  i18nCreate.ts          # per-locale instance after catalogs are loaded
  t.ts                   # isomorphic t(locale, ns, key)
  tEmail.ts              # server-only tEmail(locale, key) for the email namespace
  resources.d.ts         # i18next CustomTypeOptions from the `de` JSON modules
```

Namespaces match lazy-load boundaries:

| Namespace         | Loaded by                                                                                                                                                                                         |
| ----------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `common`          | RootDocument chrome plus every web surface (close, loading, errors)                                                                                                                               |
| `public`          | Public marketing / legal / sign-in; also nested under admin + profile shells (embedded public chrome / WYSIWYG). `CookCreateFields` / `/chef-sign-up` use `chefSignUp.*` here (not `profileCook`) |
| `publicBooking`   | Public booking-request form / plan / chat; also customer booking detail / edit and admin booking create / edit (shared form-default helpers)                                                      |
| `profile`         | Signed-in chrome both roles share (account, layout)                                                                                                                                               |
| `profileCook`     | Cook shell (`profile` route loader + `head` hydrate reload); also admin shell (shared meal/menu/offer-addon cards)                                                                                |
| `profileCustomer` | Customer shell (`profile` route loader + `head` hydrate reload)                                                                                                                                   |
| `admin`           | Admin layout                                                                                                                                                                                      |
| `email`           | `src/server/email` only. Web must not import it                                                                                                                                                   |

Route `loader`s `await i18nResourcesLoad` so catalog downloads stay inside NavigationProgress. The locale layout uses
`shouldReload: ({ cause }) => cause === 'stay'` plus `loader.staleReloadMode: 'blocking'` so client navigations that keep the same
`{-$locale}` match (e.g. landing → `/admin`, or → `/booking-request`) still re-run the loader and wait for path-derived namespaces from
`namespacesForPath` before the child paints. Without blocking, TanStack Router's default background stale reload lets the child render on
stale `common`+`public` and throw `i18n catalog not loaded`. (`loaderDeps` only sees search, so it cannot key on pathname.) The locale
layout `head()` awaits the same load so child `head()` `t()` calls work on client hydrate (loader data is restored without re-running the
loader side effect). The `admin`, `profile`, and public booking-request route loaders / `head()`s also preload their shell catalogs
(`common`+`public`+`admin`+`profileCook`; `common`+`public`+`profile`+`profileCook`/`profileCustomer`; `publicBooking`) and admin/profile
nest an `I18nProvider` with those same namespaces, matching the hydrate-safe pattern. Admin includes `profileCook` because inventory cards
(`CookMealCard`, `CookMenuCard`, …) keep cook-shell copy keys. Profile keeps `public` so cook `/profile/chef-profile` Preview (and other
embedded public chrome) can call `useT('public')` for meals / menus / about titles. Surfaces that call sync `t(locale, …)` for a locale that
is **not** the route locale (admin content-page DE/EN preview via `ContentPageView`) must nest their own `I18nProvider` (or
`await i18nResourcesLoad`) for that locale before paint — route loaders only fetch the URL locale. Fallback chain:
`fr | it | ru | nl | en → de`. Missing keys render German, never a raw key. `de` is the completeness source of truth (`npm run i18n:check`):
`en`, `fr`, `it`, `ru`, and `nl` must match the `de` key tree across all namespaces.

Keys are stable English identifiers (`logOn.title`). Values are locale copy. ICU (`i18next-icu`) for plurals/selects. Prefer two string keys
over rich-text `<Trans>`. Keep each JSON file well under ~400 keys.

UI: `useT('public')` then `t('logOn.title')`. SSR / `head()` / `src/shared`: `t(locale, 'public', 'logOn.seo.title')`. Email templates:
`tEmail(locale, 'auth.otp.body')` from `src/i18n/tEmail.ts` (server-only; do not import from `src/web`). Both isomorphic `t` / `tEmail` and
`useT` are typed against `de` catalog keys via `resources.d.ts` (`ParseKeys`). Pass **string literal** keys only. Do not build keys with
`` `path.${enum}` `` for call sites that need exhaustiveness: use a `satisfies Record<Union, string>` of exact `t(…, 'path.literal')` calls
(or `as const satisfies Record<Union, ParseKeys<'ns'>>` key maps). Open-ended runtime strings (job names, occasions) need an explicit,
commented cast. One i18n instance per locale×namespace set; do not `changeLanguage` on a shared singleton under concurrency.

SEO alternates come from `seoMeta()` over **`CATALOG_LOCALES`**. See [discovery-seo.md](./discovery-seo.md). DB-backed bilingual content
stays paired `*De` / `*En` columns until a dedicated CMS migration — see [content-model.md](./content-model.md). `contentLocaleText` uses DE
for `de`, and EN (else DE) for every other catalog locale. Fixed chrome document titles for `fr` / `it` / `ru` / `nl` prefer catalog
`*.seo.*` via `webPageSeoText` so tab titles are not English leftovers from CMS. AI-search layers sit beside SEO — see
[discovery-geo.md](./discovery-geo.md).

## Alternatives Considered

| Option                                                  | Why rejected                                                                                                                                                                        |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Keep inline `{ de, en }` literals                       | Explodes at four languages; this is the problem                                                                                                                                     |
| Paraglide JS                                            | Best per-message tree-shaking and typed `m.hello()`, and it was the previous escape hatch, but no first-class React Native/Expo story. Would also fight URL routing we already own. |
| Lingui macros                                           | Source strings stay in components (agent-context problem). PO files are worse for agents than JSON                                                                                  |
| react-intl                                              | React-centric; heavier; weak fit for emails / `src/shared` / future RN                                                                                                              |
| Router rewrite that strips locales from route awareness | Hides locale from route params; harder to type and to drive `seoMeta` / loaders                                                                                                     |
| Separate route trees per locale                         | Duplicates every page file                                                                                                                                                          |
| Colocated per-route `formatDate` / `formatCurrency`     | Drifted (`en-GB` vs `en-US`, null handling); unusable from server email/agent rendering                                                                                             |
| `Sessions.locale`                                       | Cookie + URL already cover anonymous browsing; profile language lives on `Users`                                                                                                    |
| Fifth UI locale for Swiss German                        | Written Swiss German is `de` copy plus `de-CH` formatting from region, not a catalog                                                                                                |

## Consequences

- New UI copy goes in a namespace JSON file and is read with `t()` / `useT()`. Do **not** add `{ de, en }` literals. Page-level `COPY` bags
  stay forbidden. There is no `inlineCopy` helper. Catalog values are copy only: `npm run i18n:check` rejects strings that look like leaked
  TypeScript or JSX. Cross-shell nav labels (`shell.profile` / `shell.admin` / `shell.account`) live in `common` so admin never loads the
  profile catalog and profile never loads admin. Server-built generated UI copy on GraphQL (session-event descriptions, analytics funnel
  labels, cost-breakdown titles) uses the viewer `Users.locale` as a single string, not paired `*De` / `*En` fields.
- Adding a locale means JSON files under `src/i18n/locales/{locale}/`, `CATALOG_LOCALES`, GraphQL `enum Locale`, `languageTagFromLocale` /
  `DATE_FNS_LOCALE` / `OG_LOCALE`, sitemap/hreflang (automatic once listed), and a cspell `overrides` entry for that locale tree (do not put
  `de-de` / `fr-fr` / `it-it` / `ru_ru` / `nl-nl` in the root `dictionaries` list). WhatsApp Meta templates stay DE/EN for now
  (`fr`/`it`/`ru`/`nl` recipients get English); dedicated Meta languages are optional follow-on (see [whatsapp.md](./whatsapp.md)). Source
  and English catalogs stay English-only; see [conventions.md](../conventions.md#spell-check).
- Raw transport / GraphQL / upload error bodies must not reach the UI — map via `t(locale, 'common', 'saveFailed')` or a namespace helper
  (see [conventions.md](../conventions.md#bilingual-copy)).
- A static PWA manifest (`public/manifest.json`), when present, stays brand-only; it cannot switch with the route locale.
- CMS `*De` / `*En` columns are **not** the UI catalog. Do not drive city/blog prose through i18next. A JSONB locale map is the follow-on
  when FR/IT/RU/NL editorial content is real.
- WhatsApp copy is registered per language in Meta (DE/EN today), not JSON.
- Legal bodies that are German-only stay German-only. Slack ops stay German-only.
- Day-to-day recipes (new page under `{-$locale}/`, sitemap entry, new catalog key) live in [conventions.md](../conventions.md) and the "How
  to Add Things" section of [`AGENTS.md`](../../AGENTS.md) — this ADR stays on _why_.
- Server and client share one formatting surface under `src/shared`, so email HTML and agent snapshots stay consistent with the UI.
- Changing language while signed in (switcher or deep link) always hits the mismatch gate until profile and route agree. Admin **Sign in as
  user** skips the gate for the whole impersonation session (and on entry adopts the target `Users.locale` cookie + path) so the operator
  does not rewrite that user’s language.
