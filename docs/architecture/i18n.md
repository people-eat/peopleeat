# Internationalization (i18n)

## Context

The site serves German (default) and English visitors from one codebase. Without a deliberate locale strategy, routes, SEO (`hreflang`,
sitemap), and bilingual copy drift into ad-hoc patterns — or an i18n library is adopted before the catalog justifies it.

## Decision

**Optional path parameter `{-$locale}`** (TanStack Router) with **inline** `{ de: '…', en: '…' }[locale]` literals at the call site. No i18n
library; no page-level `COPY` const (see [conventions.md](../conventions.md#bilingual-copy)).

- Default locale is `de` (unprefixed URLs: `/`, `/about`). English is prefixed: `/en`, `/en/about`.
- Canonical `Locale` (`'de' | 'en'`), `LOCALES`, and `DEFAULT_LOCALE` live in `src/shared/locale.ts`. Web-only helpers
  (`localeFromAcceptLanguage`, `localeFromParam`) re-export those types from `src/web/utils/locale.ts`.
- `languageTagFromLocale(locale)` maps to BCP-47 tags used by `Intl`: `de` → `de-DE`, `en` → `en-US`.
- `src/routes/{-$locale}.tsx` `beforeLoad` auto-redirects first-time visitors from `Accept-Language` / `locale` cookie when the preferred
  locale is not the default. Redirects and language switches go through `buildLocalePath` / `pathWithoutLocale`, which strip every leading
  non-default locale segment from the path before re-prefixing so a stale match or mismatched claimed locale cannot produce `/en/en/…`.
- Components read locale via `useLocale()` (`src/web/hooks/useLocale.ts`). The language switcher (`LanguageSwitcher`) sets the cookie and
  navigates; on public pages with a `Footer` (landing, sign-in) it lives in the footer bottom bar as quiet native-language text links
  (`Deutsch` / `English`) styled like the adjacent legal links — not ISO codes or filled pills.
- **Signed-in profile language** — `Users.locale` is mandatory (`NOT NULL`, DB default `de`). Self-registration stamps the current UI locale
  via `UserCreate.locale`; admin create defaults to `de`. Transactional lifecycle/job emails resolve locale from each recipient’s
  `Users.locale` (OTP and gift-card purchase still use request-time / snapshot locale for guests). When a signed-in user’s route locale
  differs from `Users.locale`, `LocaleMismatchGate` (first in the root startup pipeline) shows a non-dismissible dialog: confirm updates the
  profile (+ cookie), decline redirects to the profile-locale path (+ cookie). No `Sessions.locale`. Pipeline order:
  [session-startup-gates.md](../features/session-startup-gates.md).
- **Signed-in profile time zone** — `Users.timeZone` is mandatory (`NOT NULL`, DB default `Europe/Berlin`, IANA id). Self-registration
  stamps the browser zone via `UserCreate.timeZone`; admin create defaults to `Europe/Berlin` when omitted. Users edit it on Account; admins
  on the user general form. GraphQL validates with `graphql-scalars` `TimeZone`. `SessionStartupGates` loads `user.timeZone` into
  `TimeZoneProvider`; UI calls `useTimeZone()` and passes `{ locale, timeZone }` into shared date/time formatters. Anonymous visitors fall
  back to the browser zone (SSR: `DEFAULT_TIME_ZONE`). User-facing emails that format absolute times use the **recipient** `Users.timeZone`.
  Cook call wall-clock derivation uses the **cook’s** `Users.timeZone`. Slack ops and Berlin-fixed jobs stay on their own constants.
- **Display formatting** (dates, times, date ranges, month/year, participants, currency, file sizes, durations) uses isomorphic helpers in
  `src/shared` — `formatDate`, `formatTime`, `formatDateTime`, `formatDateRange`, `formatMonthYear`, `formatParticipants`, `formatCurrency`,
  `formatBytes`, `formatDuration`, `formatHms`, plus storage helper `formatIsoDate` and form helpers `centsToEuros` / `eurosToCents`.
  Locale-aware display helpers take a required `{ locale }` options object and derive the language tag internally via
  `languageTagFromLocale`. `formatCurrency` defaults to **2 fraction digits** for cook, customer, and offer-price surfaces; only admin
  overview summaries may pass `maximumFractionDigits: 0`. Date/time helpers accept an optional `timeZone` (viewer via `useTimeZone()`,
  recipient in emails, cook zone for call-slot derivation; Slack stays on its ops constant). Prefer these over local `Intl` / `date-fns`
  formatters in routes, emails, and Slack. Import from `src/shared` (barrel).
- Calendar widgets and relative time (`formatDistanceToNow*`) still use `DATE_FNS_LOCALE` from `src/web/utils/dateFnsLocale.ts` — `date-fns`
  needs its own locale objects and is not inferred from the route. The shared `Calendar` month-dropdown formatter uses that locale's `code`
  (not the browser default) so `/en/...` visitors see English month names even when the OS is German.

SEO alternates come from `seoMeta()` — see [discovery-seo.md](./discovery-seo.md). DB-backed bilingual content (when adopted) uses paired
`*De` / `*En` columns — see [content-model.md](./content-model.md). AI-search layers sit beside SEO — see
[discovery-geo.md](./discovery-geo.md).

## Alternatives Considered

| Option                                                  | Why rejected                                                                                                                                    |
| ------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| i18n library (Paraglide, react-intl)                    | Message catalogs and ICU are overkill for a two-locale site with mostly inline strings; Paraglide remains the upgrade path if the catalog grows |
| Router rewrite that strips locales from route awareness | Hides locale from route params; harder to type and to drive `seoMeta` / loaders                                                                 |
| Separate route trees per locale                         | Duplicates every page file                                                                                                                      |
| Colocated per-route `formatDate` / `formatCurrency`     | Drifted (`en-GB` vs `en-US`, null handling); unusable from server email/agent rendering                                                         |
| `Sessions.locale`                                       | Cookie + URL already cover anonymous browsing; profile language lives on `Users`                                                                |

## Consequences

- Every visitor-facing string is duplicated inline — cheap to read, easy to drift if a string is updated in only one locale. Treat identical
  `de`/`en` values as a smell unless the word is genuinely shared (brand, identical loanword like `Name`).
- Adding a locale means extending `LOCALES` / `Locale` and touching every inline object (plus cspell dictionary if needed).
- Raw transport / GraphQL / upload error bodies must not reach the UI — map via a bilingual helper or a generic `{ de, en }` fallback (see
  [conventions.md](../conventions.md#bilingual-copy)).
- A static PWA manifest (`public/manifest.json`), when present, stays brand-only; it cannot switch with the route locale.
- Day-to-day recipes (new page under `{-$locale}/`, sitemap entry) live in [conventions.md](../conventions.md) and the "How to Add Things"
  section of [`AGENTS.md`](../../AGENTS.md) — this ADR stays on _why_.
- Server and client share one formatting surface under `src/shared`, so email HTML and agent snapshots stay consistent with the UI.
- Changing language while signed in (switcher or deep link) always hits the mismatch gate until profile and route agree. Admin **Sign in as
  user** is the exception on entry: it adopts the target `Users.locale` (cookie + path) before opening `/profile`, so the gate does not fire
  from a leftover admin `/en/…` URL.
